# Failure catalog

Every failure class this harness has actually hit, and the guard that now
covers it. When something new breaks: fix it, then ADD IT HERE with its guard.
This file is why the next machine/repo doesn't pay for these lessons twice.

| # | Failure | Symptom | Guard |
|---|---------|---------|-------|
| 1 | **Revert-collapse** | Snapshot-switch to a RUNNING snapshot occasionally leaves the guest powered off moments later; next `prlctl exec` dies with "not started" (exit 255). Seen on macOS and Linux guests. | `ensure_running` before every guest run (core.sh); starts the VM if the revert collapsed. |
| 2 | **Wedged guest process** | A hung guest process (daemon holding a TUN device, stuck msiexec) outlives its host-side `prlctl exec`; the run hangs forever and the NEXT test inherits the wedge. | `run_guarded` host-side timeout (returns 124) + `guest_kill_stragglers` (repo-config process list). Guest-side: `Invoke-Guarded`/bounded stops in flavor scripts. |
| 3 | **External-drive boot** | VM booted in place off the archive drive: slow, flaky (macOS especially), wears the drive; in CI it happened *silently*. | Internal-disk-only policy in `resolve_effective_vm`: non-interactive = hard fail with guidance; interactive = clone-to-internal or abort. `vmkit doctor` flags bundles outside the internal dir and a Parallels default VM home on external storage. |
| 4 | **Host contention** | Two harness invocations (CI job + local run, or two agent sessions) stop each other's VMs mid-test; runs die with cancellations/resets that look like flakes. Worst form: a CI job lands during INTERACTIVE use and powers off the guest a human is working in — GitHub's `concurrency` group serializes CI jobs against each other and knows nothing about a local session. | Two layers. (a) `ensure_only` is per-invocation by design (one VM at a time), and CI uses a `concurrency` group that queues rather than cancels. (b) `vmkit hold` (lib/hold.sh) claims the host: `ensure_only` then REFUSES with the reason instead of stopping the guest. Authorization is by **token** (`VMKIT_HOLD_TOKEN`, from `vmkit hold --print-token`), never by VM name — the first version keyed on the name, which permitted work on the held VM and so protected every guest EXCEPT the one in use; a CI vm-test job targeting that same guest reverted it mid-provision (2026-07-26). Holds always carry a deadline (`--ttl`, default 4h) so a forgotten one can't wedge CI indefinitely; `vmkit unhold` releases, `VMKIT_IGNORE_HOLD=1` overrides, `vmkit doctor` surfaces an active hold. Belt-and-braces for long sessions: also stop the runner service, so jobs queue instead of failing. (c) **A SELF-HOLD, since 0.4.6** (lib/hold.sh, `self_hold`): `test`/`series`/`run`/`reset`/`up`/`provision` each claim the host for their own duration and release on exit and on signal. (a) and (b) both live OUTSIDE vmkit and neither closes the gap: a `concurrency` group serializes one workflow in one repository and cannot see a second self-hosted runner on the same host, another org's jobs, an agent session, or a person (downstream, that Mac already runs a runner for a different GitHub org); and `hold` was opt-in, so the invariant held by convention. One VM at a time was a property of each INVOCATION, not of the host. The record is created with `ln`, which is atomic and fails if it exists, so two jobs dispatched in the same second cannot both win. TTL is derived, not guessed: flavor timeout + `VMKIT_SELF_HOLD_MARGIN` (900s, covering the sibling stop, the memory settle, the boot wait and the push), capped at `VMKIT_SELF_HOLD_MAX` (4h) so a killed run cannot wedge the host. `VMKIT_NO_SELF_HOLD=1` restores pre-0.4.6 behaviour. What a caller SEES when the host is busy is unchanged: the same refusal, the same non-zero exit — a refused leg must fail, not go green having tested nothing. |
| 5 | **Merged-red tests** | New test suites merged while failing ("we'll fix it after") — every subsequent run is red, real regressions hide in the noise, and diagnosis re-derives everything. | Process rule: a new flavor must pass a full `vmkit series <flavor>` locally before it merges. Red = broken, always. |
| 6 | **Snapshot drift / clobber** | A "built" snapshot silently replaced with the wrong state; or missing after a botched provision — and the fix re-downloads gigabytes on a metered link. | Uniform ladder names + `vmkit checkpoint` replaces atomically; keep a PERMANENT anchor snapshot after expensive provisioning (e.g. `-toolchain`) that routine flows never overwrite; `vmkit doctor` verifies the ladder. |
| 7 | **Metered-network surprise re-downloads** | Provisioning fetches toolchains/installers from the network during a test run. | Cache-first rule: downloads happen once into `VMKIT_CACHE_DIR` on an unmetered link; the *test path only reverts snapshots and reads the cache*. Provisioning scripts must be idempotent and cache-first. |
| 8 | **Stale artifacts under test** | The guest's baked-in binary is whatever was last provisioned by hand — not the commit under test. | Artifact plumbing (`VMKIT_ARTIFACT_*`): CI-built artifacts staged into the repo are auto-discovered and passed to the guest via env; the snapshot binary is only a fallback. |
| 9 | **Guest transport quirks** | SYSTEM can't see drive letters; macOS share is TCC-EPERM under headless exec; inline multi-line exec mangles args. | Encoded in transport.sh + docs/CAPABILITIES.md. UNC on Windows, tar.gz-push (+ keepalive) on macOS, script-files-only everywhere. |
| 15 | **Silent macOS artifact push kills runner** | Job marked failed at ~10 min by GitHub ("runner lost communication") while the self-hosted Mac was still busy; test stdout later ends `RESULT=PASS`. Cause: base64-over-heredoc push of a ~15 MB binary with **zero log output for many minutes**, host saturated, runner missed job-lock renewals. | `push_file_macos` / `push_script_macos` stream binary tar.gz (prlcopy-style, ~6× faster than base64) and emit `>> still pushing …` every `VMKIT_PUSH_KEEPALIVE_SECS` (default 15). |
| 10 | **Headless-OS impossibilities asserted as failures** | macOS trust-settings / launchd system bootstrap can never succeed under headless exec; asserting them = permanent red. | `assert_or_skip` with a reason naming the covering test (guest-lib), + CAPABILITIES.md so authors know in advance. |
| 11 | **Interactive-runner TTY** | CI runner run via interactive `run.sh` has a TTY; a prompt raised there (bug or phish) can capture the operator's credentials. An unexplained bare `Password:` prompt has been observed. | Run the runner as a service (no TTY). Human rule: never answer prompts in a runner terminal. |
| 12 | **CI reruns test stale code** | `gh run rerun` on a pull_request workflow reuses the ORIGINAL merge SHA — base-branch fixes never reach a rerun. | To retest a PR against a fixed base: merge the base into the PR branch (fresh merge ref), don't rerun. |
| 13 | **Silently-skipping workflow steps** | `if: ${{ inputs.x != false }}` skips on push/PR forever (GitHub loose comparison: null == false), so a "required" leg never actually ran. | Gate dispatch-only inputs with `github.event_name != 'workflow_dispatch' || inputs.x`; verify a leg RAN (not just that the job is green) when adding it. |
| 16 | **Unbounded VM stop starves the job lease** | A leg dies at exactly ~10 min, `Abandoned`, mid-test. Host log shows a 20+ minute gap after `>> stopping other running VM: <name>` with no output. Cause: `prlctl stop --fast` on a guest wedged by a PREVIOUSLY killed leg blocks indefinitely (21.5 min observed on macOS), the runner misses job-lock renewals, GitHub reclaims the job — which leaves another wedged guest, so it **cascades** (seen: all three legs of one run dying at 10m01s). | `stop_vm` (core.sh) timeboxes the graceful stop at `VMKIT_STOP_TIMEOUT` (default 120s), emits `>> still stopping …` every 30s, then escalates to `prlctl stop --kill` and verifies. Safe because every automated caller reverts to a snapshot next. Same class as #15: silent + long + host-saturating. |
| 14 | **Runner lost communication** | Self-hosted job dies at ~10 min with every step asterisked and no step logs; annotation: "The self-hosted runner lost communication with the server". Cause: the host's uplink dropped long enough that job-lock renewals failed and GitHub expired the job server-side. Kills good work (seen twice, both mid-cargo-build, before any VM ran). | **No automatic guard — by choice.** A `workflow_run` watcher (portzero-local `.github/workflows/vm-e2e-retry.yml`) used to rerun jobs when that annotation was present, capped at 2 retries; it was deleted 2026-07-15 (`527b32c`) because a second workflow shadowing another job's outcome was not worth maintaining. Current mitigation is to keep legs SHORT so they span fewer lock renewals (see #16 — the biggest single win was timeboxing VM stop), then re-run by hand. Diagnose from `_diag/Runner_*.log`: `renewjob failed (Socket Error: TimedOut)` → `TaskAgentJobNotFoundException` → `result: Abandoned`. Note the host uplink drops these long-poll connections every 20–35 min even when idle, so the exposure is continuous; only job LENGTH is under your control. |
| 17 | **Artifact built for the wrong architecture** | Every phase of a macOS guest test reports a bare `ok=false` — install, resolver, hosts-pin, tunnel — and the run burns its full budget before failing on an unrelated-looking count of assertions. Nothing in the log says "architecture". Cause: the artifact was built on a GitHub-hosted macos runner (Apple Silicon) while the Mac hosting Parallels is Intel, so the pushed binary can't exec in the x86_64 guest ("bad CPU type in executable"). Latent whenever a build MOVES off the VM host — the two used to be the same machine, which made the match implicit and undocumented. | `assert_artifact_runnable` (testing.sh), called from `cmd_run` before the artifact is pushed: compares `lipo -archs` on the host artifact against `uname -m` from the guest itself, and refuses with both architectures named. macOS guests only — `lipo` names arches exactly as `uname` does, while ELF/PE naming would need a translation table to be better than guesswork. |
| 18 | **A typo'd flag becomes a 4-hour host hold** | `vmkit hold --list` (no such flag) printed `>> host held for <entire host> (4h00m left): --list` — reading like success while claiming the whole host. Every later `ensure_only` then refuses with reason `--list`, i.e. a CI outage, until someone runs `unhold` or four hours pass. `cmd_hold`'s catch-all treated ANY unmatched argument as reason text, so every mistyped option silently became an acquisition; `--vm`/`--ttl` with no value swallowed the next flag the same way (`--vm --ttl 60` held a VM named `--ttl`). The zero-argument typo case was already guarded (report, don't acquire) — the flag case was not. Hit 2026-07-26 while merely trying to CHECK for a hold. | `cmd_hold` rejects unrecognized `-*` arguments with usage and exit 2 instead of holding, and requires a non-flag value for `--vm`/`--ttl`. `--status` (alias `--list`) is now a real read-only query, so the natural thing to type reports instead of acquiring. Free-text reasons that genuinely start with a dash still work via `vmkit hold -- '--text'`. |
| 17 | **Guest script dies silently, exit 0** | Provisioning "succeeds" having installed nothing. A cmdlet that kills the PowerShell session (`Get-LocalGroupMember` on Win11 26100, when the group holds an unresolvable SID) produces no exception, no stderr, and `prlctl exec` still returns 0. vmkit then baked an unprovisioned guest into BOTH the checkpoint and the permanent anchor. | `cmd_provision` requires `RESULT=PASS` in the output before re-capturing anything — not merely a `RESULT=` line, so an explicit `RESULT=FAIL` at exit 0 is refused too. Silence, partial output and explicit failure all fail loudly with a reproduce command. Capture the run with `set +e` around the pipeline, never `\|\| true` (which resets `PIPESTATUS` to 0 and would defeat the pre-existing exit-code check). |
| 18 | **`prlctl exec` never returns after the script finished** | Guest prints `RESULT=PASS`, then vmkit hangs for the entire timeout and never reaches its re-capture step, so the snapshot it should have produced does not exist. Seen twice; the state had to be checkpointed by hand. | Guest-side: every `Start-Process` needs explicit `-RedirectStandardOutput`/`-RedirectStandardError`. Without it the child inherits the script's stdout handle, and any installer that leaves a service running (Docker Desktop, sshd) holds that pipe open forever so the stream never reaches EOF. End the script with `[Environment]::Exit` rather than `exit` so it drops its own handles immediately. Same root cause as row 9's `\| Out-Null` hazard, one level down. |
| 19 | **Snapshot revert silently restores HARDWARE config** | Nested virtualization, vCPU count and RAM all revert with the snapshot. Enabling nested virt, then reverting to a snapshot taken before it, silently turns it back off — and a resize applied while the VM is stopped is undone by the next revert to an older running snapshot. Docker Desktop then fails to install for no visible reason. | Apply hardware changes with the VM stopped, boot, VERIFY in-guest (`Win32_ComputerSystem`), and only then capture the checkpoint, so the config travels with the snapshot the test path reverts to. Re-check after any revert to an older rung. |
| 20 | **Credential prompt with no TTY = infinite hang** | `git clone` of a PRIVATE repo prints "Cloning into '…'" and blocks forever: git prompts for a username and `prlctl exec` provides no TTY. Two runs sat on that prompt, one for 20 minutes, while every network check (DNS, ICMP, TCP 443, small HTTPS) passed — because nothing was wrong with the network. | Set `GIT_TERMINAL_PROMPT=0` machine-wide in every guest so git fails fast instead of blocking. Better: don't fetch from a remote at all — vmkit already runs guest scripts FROM the host repo over the share, so the script's own parent directory IS the repo; copy from there. No network, no credentials in a snapshot, and the guest gets the working tree under test. Mark the copy `git config --system --add safe.directory` or git rejects it as "dubious ownership" for whichever identity did not do the copying. |
| 21 | **Windows Features-on-Demand is slow and unreliable** | `Add-WindowsCapability -Name OpenSSH.Server` took 11.5 min on one run and 19 min on the next — ~70% of an entire provision — then FAILED, leaving `prlctl exec` wedged on the dead DISM operation. It pulls from Windows Update: uncacheable, unthrottleable, unpinnable. | Install the equivalent redistributable from the offline cache instead — Win32-OpenSSH ships the same upstream project Microsoft repackages as the FoD, 6.3 MB, seconds to install. Keep `Add-WindowsCapability` only as the fallback when the cache is unavailable. |
| 22 | **The harness reports PASS for a leg that did nothing** | First run of a new flavor: the guest script cannot source its helpers, so every `assert` is `command not found`, no `RESULT=` line is printed at all, and the script dies under `set -u` — and vmkit prints `=== macos (download): PASS (40s) ===`. Two independent signals of failure were available and NEITHER was read: the absent `RESULT=` line, and the guest's non-zero exit. Worst for a brand-new flavor, where the most likely first-run mistake (row 23) produces a green run that looks like the flavor works; and it degrades quietly rather than loudly — a flavor that stops sourcing its lib after a refactor goes green, not red. Same class as #13, one level up: this is the harness itself. | `guest_result_gate` (testing.sh) reads both signals. No `RESULT=` line → **NO-RESULT** (exit 125), a distinct outcome rather than a plain FAIL because "the script asserted a failure" and "the script never got far enough to say anything" have different first debugging steps; the message names the likely cause. Nothing printed at all → **NO-OUTPUT** (a crashed interpreter still yields exit 0 through `prlctl exec`). `RESULT=PASS` with a non-zero exit → **FAIL**: the sentinel does not outrank the exit status, because everything after the last `PHASE=` line did not happen. `RESULT=SKIP` → **SKIP**, reported as itself instead of as a pass. A guest that never reached the script → **SETUP-FAILED**. `VMKIT_REQUIRE_RESULT=0` opts out of the RESULT half only; the exit status is not negotiable. Proven by fixtures broken on purpose (`tests/fixtures/vmtest/scripts/`) asserted in `tests/run.sh`, which CI runs on every push against a fake `prlctl` — a guard that cannot fail is not a guard. |
| 23 | **Only the flavor script's own directory reaches the guest** | `. "$(dirname "$0")/lib/assert.sh"` works; `. "$(dirname "$0")/../lib/assert.sh"` resolves on the HOST and is absent in the guest. vmkit pushes the script's own directory and nothing above it, which was stated in exactly one place — the run line `>> pushing script dir into guest via tar.gz: vmtest/scripts`. `guest-lib/assert.sh` said "copy this file next to your flavor scripts", which reads equally well as "beside the scripts directory". A five-minute mistake on its own; combined with row 22 it is a five-minute mistake that produces a GREEN leg. | `vmkit init` scaffolds `vmtest/scripts/lib/` with the helpers already copied in, plus stub flavor scripts that source them — the correct layout is now the default and the copy step is gone from the setup path. `guest_script_lint` warns when a flavor script sources a path above its own directory, before any VM boots. The guest-lib headers and CAPABILITIES.md ("All guests") state the granularity outright. And row 22 means getting it wrong now fails instead of passing. |
| 24 | **One non-ASCII character makes a `.ps1` fail to parse — and the error names the wrong line** | `At ...\download.ps1:77 char:50 ... Missing closing '}' in statement block or type definition`, pointing at a line whose braces are balanced (and so are the file's). Cause: Windows PowerShell 5.1 reads a UTF-8 file with **no BOM** as CP1252, so an em dash (`E2 80 94`) decodes to three characters ending in U+201D — a smart closing quote PowerShell honours as a string delimiter. One inside a double-quoted message ends the string early and everything after it parses as code, which is why the parser complains about braces several lines later in a place with nothing wrong with it. Harmless inside a `#` comment (parsing stops at end of line), fatal inside a string — and "only in strings" is not a rule anyone applies reliably while writing prose in a comment. `guest-lib/assert.ps1` itself shipped with an em dash on line 8: safe where it sat, but it is the file every repo is told to copy. | `guest-lib/` and `templates/scaffold/` are ASCII-only, enforced by `tests/check-ascii.sh` in `just check` and in CI. `vmkit check-scripts` applies the same rule to a consuming repo's flavor scripts and `bash -n`s the shell ones; `vmkit test` runs it before booting anything — two seconds of grep instead of forty of boot, and the refusal names CP1252 rather than a brace. The alternative fix, writing `.ps1` with a UTF-8 BOM, was rejected: a BOM is invisible, an editor or a `sed` drops it silently, and the constraint then depends on a byte nobody can see. |
| 25 | **PowerShell helpers that answer a different question than they appear to** | Three, all quiet. (a) `Invoke-Guarded` runs its block via `Start-Job` — a SEPARATE PROCESS — so `$LASTEXITCODE` and any variable the block sets never come back and `Receive-Job` output is discarded. `Phase 'x' ($ok -and $LASTEXITCODE -eq 0)` reads naturally and measures the CALLER's exit code. It answers "did this hang", never "did this succeed". (b) The obvious replacement fails again: `Start-Process -PassThru` **without `-Wait`** never populates `ExitCode` — it reads back EMPTY, not non-zero — so every phase checking one failed while the command had plainly worked, output file on disk beside it. A parameterless `WaitForExit()` afterwards does not fix it; only `-Wait` does, which means you cannot have a per-command timeout AND a reliable exit code out of `Start-Process`. (c) Any `Write-Output` inside a helper joins its RETURN VALUE: one diagnostic line made a wrapper return `@(message, bool)`, `Phase` failed to bind its `[bool]`, threw, and the phase **vanished from the report** — a helper reporting a failure by deleting it. `Invoke-Guarded` did exactly this to itself: on timeout it emitted `WARN=...` to the success stream and then `return $false`, so the caller received a two-element array, which is truthy — a wedged step read as SUCCESS. | `Invoke-Native` in guest-lib/assert.ps1: `Start-Process -Wait -PassThru` with explicit log files, returning `@{ Completed; ExitCode; Out; Err }`, plus `Ran-Ok` for the `[bool]` `Phase` wants. Lifted from the downstream implementation proven on a Windows 11 guest under `prlctl exec` as SYSTEM. Deliberately NO in-guest timeout: vmkit already owns that (`VMKIT_FLAVOR_*_TIMEOUT` + `VMKIT_KILL_WINDOWS`) and does it better, and a second weaker timeout bought nothing except the broken exit code. `Invoke-Guarded` keeps its one job and its doc comment now says what it cannot do; its timeout warning moved to `[Console]::Error.WriteLine` so it returns a plain `$false`. All three are in CAPABILITIES.md's Windows section, where someone writing a flavor script will meet them first. |
| 26 | **A finished run sits silent until its timeout expires — host-side this time** | The guest prints `RESULT=PASS` and vmkit then emits nothing at all until the full `VMKIT_RUN_TIMEOUT` elapses, never reaching its next step. Indistinguishable in a log from the guest-side handle-inheritance hang above, and both can be true at once. Cause: `run_guarded`'s timeout and heartbeat timers are subshells that inherit the run's stdout/stderr, and `kill`ing a subshell does not kill the `sleep` it is blocked in — the orphaned `sleep` holds the write end of the pipe open. Any caller that PIPES the output then waits on the pipe rather than on the command: `cmd_provision` already did, and reading the `RESULT=` line (row 22) requires it everywhere. Found by vmkit's own self-test, where two-second cases took thirty. | The killer subshell drops both streams (`>/dev/null 2>&1`) since it never prints; the heartbeat keeps stderr but polls in 1s steps so it exits on its own within a second of the command finishing, instead of being killed mid-`sleep`. `tests/run.sh` asserts a finished run returns in well under its flavor timeout. |
